# 用 AI 做了一个 macOS 剪贴板工具：Zcopys 的制作全过程与提示词

> 从菜单栏小工具，到底部全宽卡片面板；从「能用」到「好用」。本文记录我用 Cursor / AI 协作做出 Zcopys 的真实路径，以及可复用的提示词。

---

## 一、先说结果：Zcopys 是什么

**Zcopys** 是一个常驻 macOS 菜单栏的剪贴板增强工具：

- 自动记录文本、链接、文件、图片
- `⌘⇧V` 呼出底部横向铺满的玻璃面板
- 横向卡片浏览，支持搜索、置顶、删除
- **Useful Links**：收藏常用链接/文本，可手动添加，也可从历史一键收藏
- 点击卡片后写回剪贴板，并尽量自动粘贴到刚才的输入框
- 敏感内容（验证码、卡号、Token、私钥等）自动跳过

技术栈很克制：Swift / SwiftUI + AppKit，macOS 14+，Swift Package Manager 打包成 `.app`。

---

## 二、为什么要做它

一开始仓库里已经有一个雏形：菜单栏应用、剪贴板轮询、历史列表、基本打包脚本。功能能跑，但交互还是「竖列表 + 搜索框」那一套，离日常高频使用还有距离。

我想要的体验更接近现代启动器：

1. **呼出即用**：全局快捷键
2. **一眼可辨**：卡片化，类型有颜色区分
3. **点一下就进输入框**：不是只复制，还要粘贴
4. **有自己的收藏夹**：常用命令、路径、链接不淹没在历史里

于是决定：不推倒重来，而是在现有工程上迭代——这比从零写更快，也更适合和 AI 协作。

## 三、真实制作过程（按时间线）

### 1. 先摸清家底

第一件事不是改 UI，而是让 AI **分析现有项目**：模块怎么拆、数据存在哪、热键怎么做、有没有测试和打包链路。

产出很清楚：

- `ClipboardMonitor` 轮询剪贴板
- `ClipboardStore` 负责去重、置顶、敏感过滤、JSON 持久化
- `HotkeyMonitor` + `NSPanel` 负责呼出
- 已有 `package_app.sh` 可打 `.app` / zip / dmg

**结论：** 业务内核可用，缺的是产品交互层。

### 2. 用设计图锚定 UI，而不是空口描述

我丢了一张横向卡片 + 玻璃拟态的设计图，明确说：「把弹出页面换成这个 UI」。

这里有个关键决策：设计图里有 **Useful Links / + / ⋯**，现有产品没有。我和 AI 做了范围确认：

- 搜索：点放大镜再展开（更贴设计图）
- Useful Links：做成可编辑收藏，支持手动添加 + 从历史收藏

然后再进入「设计 → 计划 → 实现」，避免一上来就改代码改偏。

### 3. 先写 Spec / Plan，再动手

对这种「UI 大改 + 新模块」的任务，最值钱的不是立刻生成 500 行 Swift，而是：

1. 冻结布局与交互规则（面板尺寸、颜色启发式、键盘左右选择）
2. 冻结数据模型（`UsefulLink`、持久化路径、去重规则）
3. 拆成可验证任务（Store → Presentation → AppState → Panel → UI → 文档）

之后按任务推进：单测先行，再接线，再打包。核心收益是：**返工变少，AI 也不容易「顺手加一堆没要的功能」。**

### 4. 真机一测，问题才开始「变成人话」

单元测试全绿，不代表产品可用。真正上机后，连续碰到一串「只有真机才知道」的问题：

| 现象 | 根因（简化） | 处理方向 |
|------|--------------|----------|
| 点卡片没有进输入框 | 只写了剪贴板，没自动粘贴 | 记录前台应用 → 关面板 → 激活原应用 → AX 写入 / 模拟 ⌘V |
| `⌘⇧V` 打不开面板 | `NSEvent` 全局监听依赖辅助功能，修饰键判断过严 | 改用 Carbon 系统热键注册 |
| 面板位置不对 | 居中固定宽高 | 改为贴屏幕底部、横向铺满 |
| 搜索框无法输入 | `nonactivatingPanel` 无法成为 key window | 自定义可成为 key 的 Panel，输入时放行按键 |
| 辅助功能「开了又关」 | 临时签名每次重建身份 + 点卡片时 `hide`/反复弹窗冲掉授权 | Development 证书签名、装到 `/Applications`、停止乱弹权限 |
| 图标/品牌 | 设计图有水印、状态栏还是系统符号 | 去水印生成 App Icon + 白底灰图标状态栏，并改名 **Zcopys** |

这一段对「AI 做桌面应用」特别有启发：**系统权限、焦点、签名、面板是否可成为 key，是 AI 最容易写“看起来对、跑起来不对”的地方。** 你要用现象描述问题，而不是只说「修一下」。

### 5. 收尾：命名、安装、可分发

最后把工程名和应用名统一成 **Zcopys**：

- 模块 / 可执行文件 / `.app` 名称
- Bundle ID：`com.local.zcopys`
- 数据目录：`~/Library/Application Support/Zcopys/`（兼容迁移旧数据）

打包脚本会生成图标、签名、安装到 `/Applications/Zcopys.app`，并产出 zip / dmg。

## 四、我学到的协作方法

### 1. 先定边界，再让 AI 写代码

比如 Useful Links 要不要做、搜索怎么交互、自动粘贴算不算范围——这些用选择题一次性定死，比写完再改便宜十倍。

### 2. 用「现象 + 期望」描述 Bug

有效：

> 点击卡片后，内容没有粘贴进刚才聚焦的输入框；期望：关闭面板并自动粘贴。

低效：

> 粘贴有问题，帮我看看。

### 3. 桌面端优先谈「系统约束」

macOS 上高频踩坑：

- 辅助功能（Accessibility）
- Panel / key window / 输入焦点
- 全局热键
- 代码签名与 TCC 权限持久化

提示词里点名这些关键词，AI 更容易命中根因。

### 4. 设计图 > 长段文字

UI 用一张图 +「换成这个」往往比写三页视觉规范更稳。

## 五、可复用提示词（按阶段）

下面这些提示词基本可直接复制，把产品名/截图换成你的即可。

### 1）分析现有项目

```text
帮我分析下这个项目：它是做什么的、模块怎么分层、数据存在哪、如何运行/测试/打包。
请用简洁结构说明：目标用户、核心流程、技术栈、可改进点。
```

### 2）按设计图改 UI（先定范围）

```text
帮我把弹出的页面换成这个 UI（附图）。
先不要写代码：确认哪些设计元素本次必须实现，哪些可以先占位。
Useful Links / 搜索 / “+” / “⋯” 分别怎么处理？给我 2–3 个方案和推荐。
```

### 3）冻结需求（选择题模板）

```text
Useful Links 内容来源你更希望：
A. 仅手动添加
B. 仅从剪贴板历史收藏
C. 两者都要（推荐的话请说明为什么）
请只问一个关键问题。
```

### 4）要设计文档，不要直接开写

```text
按我们确认的范围，给出实现设计：布局、数据模型、交互、文件改动清单。
分段确认，我回复 ok 后再进入实现计划。
```

### 5）实现时要求可验证

```text
按计划实现，优先 TDD：先写失败测试，再写最小实现，再跑通测试，再提交。
不要做计划外功能。完成后打包成可双击的 .app 并启动。
```

### 6）真机 Bug：自动粘贴

```text
点击卡片后，内容没有自动粘贴进刚才的输入框。
请修复：关闭面板 → 回到之前的前台应用 → 自动粘贴。
说明是否依赖辅助功能权限，并重新打包安装。
```

### 7）真机 Bug：全局快捷键

```text
⌘⇧V 无法打开面板。
请排查 Hotkey/Accessibility/修饰键判断，优先使用更可靠的系统热键注册方式，并重新打包启动。
```

### 8）真机 Bug：焦点与输入

```text
搜索框无法输入文字。
可能是 NSPanel 无法成为 key window，或本地按键监听拦截了字符键。
请修复并重新打包。
```

### 9）真机 Bug：权限反复弹窗

```text
点击卡片复制时，辅助功能权限弹窗反复出现，授权后下次又关闭。
请停止在业务路径里反复 prompt；用稳定签名并安装到 /Applications；无权限时至少保证已复制到剪贴板。
```

### 10）视觉与品牌

```text
去掉这张图的水印，替换应用图标和状态栏图标。
状态栏做成白底灰色图标（非 template 自动着色）。
把工程名和应用名都改成 Zcopys，并更新打包/安装路径。
```

### 11）要一篇对外内容时

```text
根据我们做这个 App 的真实过程，写一篇可发布文章：动机、过程、踩坑、方法总结，并整理关键提示词。语气像技术分享，不要写成广告。
```

## 六、如果你也想做同款，最小路径

1. 先有一个能跑的菜单栏壳子（或 clone 类似工程）
2. 用一张 UI 图冻结交互
3. 让 AI 写 Spec + 分任务实现
4. **每天至少真机测一次**：热键、焦点、粘贴、权限
5. 用开发者证书签名并固定安装到 `/Applications`
6. 最后再改名、换图标、写介绍

---

## 七、写在最后

Zcopys 不是「一句提示词生成完整 App」的神话故事。它更像一次高效的结对：我负责产品判断和真机验收，AI 负责分析、改代码、补测试、打包。

真正拉开差距的，是这些问题有没有被问清楚：

- 这次到底做哪些、不做哪些？
- 失败时用户该看到什么？
- 系统权限丢了怎么办？
- 你怎么证明它真的好用了？

把这些写进提示词里，AI 才会从「代码生成器」变成「可靠的实现搭档」。
